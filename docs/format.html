Format specification

Tesseract's binary format: a fixed 264-byte header with the magic TSCR, followed by a stream of XChaCha20-Poly1305 encrypted chunks. Format v2 adds multi-recipient messages; all bytes are little-endian unless stated otherwise.

Message header (264 bytes)

The entire header is the AAD (additional authenticated data) of every chunk. Changing a single byte makes decryption fail.

Version 2 (multi-recipient). The field at offset 40 then holds a recipient count (u32, little-endian) instead of a public key; bytes 44–71 are reserved and must be zero. The per-recipient key blocks follow the header — see the multi-recipient key schedule.

Key schedule

Mode 1 — public-key (hybrid)

dh_eph  = X25519(eph_sk, recipient_pk)          # forward secrecy
dh_stat = X25519(sender_sk, recipient_pk)       # identity binding (zero when anonymous)
master  = BLAKE2b-256(key = dh_eph,
                      in  = dh_stat || salt || "tesseract-kdf-v1")

Mode 1, format v2 — multi-recipient

A random 32-byte data key protects the payload; it is wrapped once per recipient using that recipient's own DH secret — the same wrap_i derivation as v1, but computed per recipient. One block of 80 bytes is emitted per recipient, in the order passed to the API: 

block_i = recipient pk (32) || XChaCha20-Poly1305(key = wrap_i,
                                   msg = data_key, nonce = base_nonce,
                                   aad = header(264) || recipient pk) (48)

wrap_i  = BLAKE2b-256(key = X25519(eph_sk, recipient_i_pk),
                      in  = X25519(sender_sk, recipient_i_pk) || salt || "tesseract-kdf-v1")

The decryptor scans the blocks for its own public key, derives the same wrap_i and unwraps the data key — then proceeds exactly as in v1 (payload chunks under the data key). A message that is not addressed to your key is rejected with a dedicated error. The 264-byte header remains the AAD of every chunk, and each block is wrapped with AAD header || recipient pk, so blocks cannot be transplanted from another message or silently reordered.

Mode 2 — passphrase

master = Argon2id(passphrase, salt, ops, mem)   # ops/mem from the header

For chunk i

subkey_i = crypto_kdf(32, i+1, "TSCHNK01", master)
nonce_i  = base_nonce XOR (i in the last 8 bytes, big-endian)
aad_i    = header(264) || u64be(i) || u8(final)
ct_i     = XChaCha20-Poly1305(subkey_i, nonce_i, pt_i, aad_i)
Why is the header the AAD of every chunk? Because each chunk is bound to the header + sequence number + final marker, any reorder, splice, or truncation attempt is detected cryptographically — not just by a checksum.

File framing

v1: header(264) || (u32le len(ct_i) || ct_i)*
v2: header(264) || block_1(80) … block_N(80) || (u32le len(ct_i) || ct_i)*

Each chunk is wrapped with its length (4 bytes little-endian) followed by the ciphertext. The last chunk is marked by the final flag in the AAD. An empty message is represented as one final chunk containing 0 bytes of plaintext.

Armor (PEM-like)

Binary data can be encoded as base64 text with labeled delimiters:

-----BEGIN TESSERACT MESSAGE-----
b64
-----END TESSERACT MESSAGE-----

Decryption & inspect detect armored input automatically.

Key files (TSK1 / TSK2 / TSKp)

FormatSizeContents
TSK1 — private (plain)164 magic(4) + x_pk(32) + e_pk(32) + x_sk(32) + e_sk(64)
TSK2 — private (locked)232 magic(4) + x_pk(32) + e_pk(32) + salt(16) + ops(4) + mem(8) + nonce(24) + secret_aead(112)
TSKp — public68 magic(4) + x_pk(32) + e_pk(32)

In TSK2, the private part — x_sk(32) + e_sk(64) — is encrypted with XChaCha20-Poly1305 under the key Argon2id(passphrase, salt, ops, mem) using the AAD context "tesseract-key-v1"; the last 16 bytes are the AEAD tag. The public part is deliberately stored in the clear so fingerprints & public-key export work without a passphrase.

Anti-DoS. When reading untrusted headers/blobs, Argon2id parameters are hard-capped: at most 16 ops and 4 GiB of memory, with a 64 KiB memory minimum. This prevents hostile files from draining memory.

All sensitive material is sodium_memzero'd after use; private keys are sodium_mlock'd. The tool never uses its own RNG — only libsodium's randombytes_buf.
