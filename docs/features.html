Key management

Each identity is an X25519 key (encryption) and an Ed25519 key (signing) bundled in one file. Three file formats exist — see the format spec:

FileContentWhen
NAME.key (TSK1)Both secret keys, in the clearDefault key generation
NAME.key (TSK2)Both secret keys encrypted under a passphrase; public halves stay readableGenerated with --passphrase
NAME.pub (TSKp)Public halves onlySafe to share

keygen --passphrase protects the private key with Argon2id (libsodium's MODERATE cost by default, tunable with --kdf-ops N and --kdf-mem MB). The public half is deliberately left in the clear so fingerprints and pubkey export still work without the passphrase.

In memory, secret material is zeroized with sodium_memzero when freed, and sodium_mlock pins the secret scalars so they are not swapped to disk.

# generate a keypair whose private key is locked
tesseract-crypt keygen -o alice --passphrase

# export the public key (prompts for the passphrase)
tesseract-crypt pubkey -k alice.key -o alice.pub

# who am I?
tesseract-crypt info -k alice.key

Hybrid public-key encryption

The default mode. Every message gets a fresh ephemeral X25519 key, so one recipient key can decrypt thousands of messages without the recipient's secret key ever being exposed:

dh_eph  = X25519(eph_sk, recipient_pk)          # forward secrecy
dh_stat = X25519(sender_sk, recipient_pk)       # identity binding
master  = BLAKE2b-256(key = dh_eph,
                      in  = dh_stat || salt || "tesseract-kdf-v1")

The second DH term binds the identity: a message can only be opened by the intended recipient, and an attacker who replaces the ciphertext cannot make it decrypt under someone else's key. Pass -k sender.key to encrypt with that sender term and to sign (see below); without it the message is anonymous.

Multi-recipient messages (format v2)

Repeat -r to encrypt one message for a whole team. A random 32-byte data key encrypts the payload; the data key is then wrapped once per recipient under that recipient's own DH secret:

tesseract-crypt encrypt -r alice.pub -r bob.pub -r carol.pub \
                        -k alice.key -i secret.txt -o team.enc

Cost per extra recipient is a single X25519 operation + one 80-byte key block — negligible next to any real payload. A decryptor that is not a recipient is rejected with a dedicated error rather than a generic authentication failure, so "this is not for you" is distinguishable from "this is corrupt".

Passphrase mode

When you have no public key to encrypt to, use a passphrase: --passphrase derives the master key with Argon2id (memory-hard) from the salt in the header.

# encrypt a file / a string with just a passphrase
tesseract-crypt encrypt --passphrase -i note.txt -o note.enc
tesseract-crypt encrypt --passphrase --text "satu kalimat"

# decrypt it
tesseract-crypt decrypt --passphrase -i note.enc -o note.txt
Cost. Argon2id is deliberately expensive and runs on both sides. On the reference machine it costs ~1.6 s before any payload is touched, so passphrase mode is for occasional data, not for bulk pipelines. See performance.

Parameters written into the header are hard-capped when reading untrusted input (≤ 16 ops, 4 GiB) so a hostile file cannot exhaust memory.

Sign-then-encrypt

Passing -k sender.key to encrypt makes the tool sign the plaintext with Ed25519ph (streaming variant) and store the 64-byte signature in the header. Because the whole header is the AAD of every chunk, the signature is verified as part of decryption — before a single plaintext byte is written to disk.

--no-sign skips it, and anonymous encryption is simply encrypt without -k.

Detached signatures

Independent of encryption, for release artifacts and patches:

tesseract-crypt sign   -k alice.key -i release.tar.gz -o release.tar.gz.sig
tesseract-crypt verify -k alice.pub -i release.tar.gz -s release.tar.gz.sig

Uses the same Ed25519ph construction as sign-then-encrypt, so large files are streamed and never buffered whole.

Streaming, chunking & armor

Chunked AEAD

The payload is encrypted in independently authenticated chunks (default 64 KiB, tunable --chunk-size from 4 KiB to 16 MiB). Each chunk gets its own subkey derived via crypto_kdf, its own nonce (base nonce XOR'd with the chunk index) and an AAD of header || index || final. That is what makes reorder, splice and truncation attacks fail cryptographically instead of silently corrupting output.

When is it streaming?

OperationMemory behaviour
encrypt/decrypt file → fileStreaming — constant memory regardless of file size (tess_seal_file / tess_open_file)
stdin / stdout / --textBuffered — the whole input is held in memory
sign / verifyStreaming (Ed25519ph)

Armor

Output that ends up on a TTY is wrapped as PEM-like base64 automatically; --armor forces it, and decrypt/inspect detect armored input automatically:

-----BEGIN TESSERACT MESSAGE-----
...
-----END TESSERACT MESSAGE-----

Decryption guarantees

  • Verify-before-write. Ciphertext goes to a .part file that is renamed to its final name only after the AEAD (and, when present, the signature) succeeds. Unauthenticated data never reaches the destination path.
  • Armored input is auto-detected, so pasting a block of base64 back into the tool just works.
  • Sender pinning with --require-signer signer.pub: if the message was signed by anyone else (or not signed), decryption fails with exit code 3 and no output file is written.
  • Recipient check. A v2 message that is not addressed to your key is rejected explicitly.
  • Truncation/reorder detection falls out of the chunk AAD design — cutting the stream short is detected.

Inspection

Read metadata without any key and without decrypting:

$ tesseract-crypt inspect -i team.enc
format version : 2
mode           : public-key
recipients     : 3
signed         : yes

Portability, build & testing

  • Platforms. Linux, Windows (MSVC, MinGW, MSYS2), macOS, BSD — the same binary name everywhere (tesseract-crypt, plus the tscrypt alias).
  • Build. Plain CMake ≥ 3.16 against libsodium (libsodium-dev, or vcpkg). Options: TESS_BUILD_CLI, TESS_BUILD_TESTS, TESS_SANITIZE (ASan+UBSan), TESS_WARNINGS_AS_ERRORS, TESS_FUZZ (libFuzzer harnesses).
  • Test suite. Eight ctest targets covering roundtrip, tamper, armor, key formats, file I/O, detached signatures, published known-answer vectors and multi-recipient — the same suite is built and run on every platform in CI, plus an ASan/UBSan job and three fuzzers.
  • Distribution. A GPG-signed APT repository for Debian/Ubuntu amd64, RPM packages (Fedora/RHEL/openSUSE) and a prebuilt Arch PKGBUILD, plus GitHub Release artifacts.
