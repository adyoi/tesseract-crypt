Encryption speed

What Tesseract costs in seconds and MiB/s, measured end-to-end through the CLI. The headline: symmetric payload throughput is fast, and the only expensive step is Argon2id in passphrase mode.

Reference numbers Reproduce it Features

Methodology

  • Measured through the actual tesseract-crypt CLI, so the numbers include process start-up, file I/O and per-chunk framing — not just the raw cipher.
  • Best of 3 runs (scripts/bench.sh), which removes first-run cold-cache and antivirus noise.
  • Payload: 16 MiB of random data, default 64 KiB chunks (except the chunk-size rows).
  • Release build (-DCMAKE_BUILD_TYPE=Release), TESS_WARNINGS_AS_ERRORS=ON, upstream libsodium.
Reference host. Intel Core i3-2330M @ 2.20 GHz (2 cores, 2011 Sandy Bridge) under WSL2 — a deliberately modest, bandwidth-limited machine. Modern CPUs are far faster; treat the table as a lower bound and a way to compare operations with each other.

On this host a single 16 MiB file encrypts in well under a second, and the same run repeats to within roughly 2×. Differences between the chunk-size rows are inside that noise band — they do not indicate a real advantage for one chunk size over another.

Reading the numbers

Argon2id dominates passphrase mode

Look at the gap: public-key encryption of 16 MiB is ~0.8 s, while passphrase encryption is ~4.4 s. Most of that difference is the Argon2id key derivation (~1.6 s, and it runs again on decrypt), not the cipher. If you encrypt a lot of data with a passphrase, derive one key and encrypt many messages under it instead.

Payload throughput scales with the CPU

XChaCha20-Poly1305 and BLAKE2b are not the bottleneck here — this 2011 dual-core is. On a modern desktop core, libsodium's AEAD typically streams at 1–2 GiB/s and Ed25519ph signing at several hundred MiB/s, i.e. 20–100× these figures. The CLI adds chunk framing and one extra pass for signing.

Recipients are cheap, signing adds a pass

Each extra recipient costs one X25519 + one 80-byte key wrap — a rounding error on any real payload (see how close the 3-recipient rows are to the 1-recipient ones). Sign-then-encrypt reads the plaintext once more to produce the streaming Ed25519ph signature.

Chunk size barely matters

4 KiB → 1 MiB chunks all land in the same band. Use the default 64 KiB unless you have a reason: smaller chunks detect corruption sooner and keep memory lower; larger chunks reduce framing overhead on very fast disks.

Memory

Encryption and decryption between two files are streaming: memory is constant (a few chunk buffers) no matter how large the file is. Buffered paths — stdin/stdout, --text and passphrase encryption — hold the whole input in memory. Passphrase mode additionally allocates the Argon2id working set (256 MiB at the default MODERATE setting).

Reproduce it

The benchmark is a tiny POSIX shell script that shells out to the CLI, so it runs on Linux, macOS and MSYS2/MinGW on Windows:

# build first
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# BIN [SIZE_MB]  — best of REPS (default 3) runs
scripts/bench.sh build/tscrypt 16

# more repetitions for a quieter number
REPS=5 scripts/bench.sh build/tscrypt 64
Windows note. With real-time antivirus enabled the first run of each command can be 10× slower while the scanner claims the executable and DLLs. The script's best-of-N handles this; steady-state numbers are close to Linux on the same hardware.
